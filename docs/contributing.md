## 创建新 Skill 指南

### 核心原则

Skill 遵循**渐进式披露**原则：核心定义简洁精炼，详细资料按需加载。

### 文件结构

```
skills/your-skill/
├── SKILL.md              # 核心定义（<500行）
└── references/           # 细节资料（按需引用）
    ├── workflows.md      # 工作流程
    └── research/         # 研究资料
        └── ...
```

### SKILL.md 规范

`SKILL.md` 是 Skill 的核心文件，**必须控制在 500 行以内**，包含以下关键要素：

#### 1. 心智模型（3-7 个）

定义该领域的核心思维框架，帮助 AI 理解问题本质：

```markdown
## 心智模型

1. **模型名称** — 一句话描述
   - 应用场景
   - 关键原则
```

#### 2. 决策启发式

提供明确的决策规则，减少 AI 的不确定性：

```markdown
## 决策启发式

- 当 X 情况时 → 采用 A 方案
- 当 Y 情况时 → 采用 B 方案
- 默认情况 → 采用 C 方案
```

#### 3. 触发条件

定义 Skill 何时被激活：

```markdown
## 触发条件

- 用户提到关键词：xxx、yyy
- 任务类型匹配：zzz
- 上下文包含：...
```

#### 4. 诚实边界

明确 Skill 的能力范围和局限性：

```markdown
## 诚实边界

- 本 Skill 擅长：...
- 本 Skill 不适用于：...
- 需要人工判断的情况：...
```

### 质量门限

新 Skill 必须达到 **≥80 分**（满分 100）的质量评估：

| 维度 | 权重 | 评估要点 |
|------|------|----------|
| 心智模型清晰度 | 25% | 是否准确、易理解 |
| 决策启发式实用性 | 25% | 是否可操作、覆盖全面 |
| 触发条件准确性 | 20% | 是否精准匹配场景 |
| 诚实边界明确性 | 15% | 是否坦诚局限 |
| 文档质量 | 15% | 格式规范、表述清晰 |

## 创建新 Agent 指南

### Frontmatter 必填字段

每个 Agent 文件必须包含 4 个核心字段：

```yaml
---
name: agent-name          # Agent 名称（kebab-case）
role: 角色描述             # 一句话说明 Agent 的职责
model: claude-sonnet-4-20250514       # 推荐使用的模型
tools:                    # Agent 可使用的工具列表
  - read_file
  - search_codebase
  - run_in_terminal
---
```

### 安全防护基线

所有 Agent 必须遵守以下安全准则：

- **最小授权原则** — 只授予完成任务所需的最少工具权限
- **不执行危险操作** — 禁止 `rm -rf`、`sudo` 等高危命令
- **数据保护** — 不泄露用户隐私信息或 API 密钥
- **操作可逆** — 优先选择可撤销的操作方式

### 质量门限

新 Agent 必须达到 **≥85 分**（满分 100）的质量评估：

| 维度 | 权重 | 评估要点 |
|------|------|----------|
| 角色定义清晰度 | 20% | 职责明确、不越界 |
| 安全防护完整性 | 30% | 遵守安全基线 |
| 工具使用合理性 | 25% | 最小授权、使用得当 |
| 输出质量 | 25% | 完成任务的效果 |

## 提交流程

### 1. Fork 项目

在 GitHub 上 Fork 本仓库到你的账号下。

### 2. 创建分支

```bash
git checkout -b feat/your-feature-name
# 分支命名规范：
# feat/xxx   — 新功能
# fix/xxx    — 修复问题
# docs/xxx   — 文档改进
# skill/xxx  — 新 Skill
# agent/xxx  — 新 Agent
```

### 3. 开发并通过质量检查

- 确保文件结构符合规范
- Skill 核心文件不超过 500 行
- 通过 Markdown lint 检查
- 包含所有必要的元素

### 4. 提交 Pull Request

```bash
git add .
git commit -m "feat: add xxx skill"
git push origin feat/your-feature-name
```

在 GitHub 上创建 PR，填写：

- **标题**：简洁描述变更内容
- **描述**：详细说明改动原因和内容
- **关联 Issue**：如果有对应的 Issue，请关联

### 5. 等待审查

维护者会在 **3-5 个工作日**内审查你的 PR。审查期间可能会有修改建议，请积极响应。

## 代码规范

### Markdown 格式标准

- 使用 ATX 风格标题（`#` 而非下划线）
- 标题层级不跳级（`##` 后不直接用 `####`）
- 代码块必须标注语言类型
- 列表项之间保持一致的空行风格
- 文件末尾保留一个空行

### 命名约定

| 类型 | 格式 | 示例 |
|------|------|------|
| Skill 目录 | kebab-case | `karpathy-guidelines` |
| Agent 文件 | kebab-case.md | `claudecode-expert.md` |
| 文档文件 | kebab-case.md | `getting-started.md` |
| 引用目录 | 小写单词 | `references/` |

### 文件组织规则

- Skill 放在 `skills/` 目录下
- Agent 放在 `agents/` 目录下
- 项目模块放在对应分类目录下（`crawl/`、`project/`、`team/`）
- 文档放在 `docs/` 目录下

## 社区准则

### 行为准则

- 尊重每一位贡献者，保持友善和专业的交流态度
- 不允许任何形式的骚扰、歧视或人身攻击
- 聚焦技术讨论，避免无关争论
- 对新手友好，耐心解答问题

### 沟通方式

| 渠道 | 用途 |
|------|------|
| **Issues** | 报告 Bug、提出功能建议 |
| **Discussions** | 开放讨论、提问交流、分享想法 |
| **Pull Requests** | 代码审查、具体技术讨论 |

### 响应时间预期

- **Issue 回复**：1-3 个工作日
- **PR 审查**：3-5 个工作日
- **紧急安全问题**：24 小时内

> **注意**：维护者为志愿服务，请理解响应可能有延迟。如果超过预期时间未收到回复，可以礼貌地在原帖中 @提醒。
