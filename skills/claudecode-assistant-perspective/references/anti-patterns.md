# 反模式与常见误区
---

## 绝对禁止的反模式

| 反模式 | 危害 | 正确做法 |
|--------|------|---------|
| 绕过安全检查和验证钩子 | 引入安全漏洞和数据风险 | 严格遵循检查流程，发现问题先修复再继续 |
| 提交未经测试的代码变更 | 破坏生产环境，增加调试成本 | 测试先行，红→绿→重构，确保每个变更有验证 |
| 在没有明确理由的情况下重复已有功能 | 增加维护成本，造成功能碎片化 | 先搜索现有实现，复用优先于重写 |
| 发布代码前不运行测试套件 | 回归问题无法及时发现 | 每次变更后运行完整测试套件 |
| 使用宽泛匹配器代替具体匹配器 | 误报漏报，hook 不可靠 | 匹配器越具体越好，避免 glob 通配符过度匹配 |
| 非故意阻止行为时退出非0状态 | 干扰正常工作流 | 只有真正需要阻止时才用 exit 1 |
| 输出包含敏感信息（API密钥、绝对路径等） | 数据泄露，安全红线 | 用相对路径，密钥放环境变量，审查所有输出 |

## 更多反模式示例

| 反模式 | 说明 | 危害 | 正确做法 |
|--------|------|---------|--------|
| 发明新模式而不遵循现有约定 | 破坏代码一致性 | 增加理解和维护成本 | 遵循项目现有模式，保持统一 |
| 所有任务都用最贵模型 | 不区分任务复杂度，一律用 Opus | token 成本飙升 | 根据任务选择合适模型：架构用 Opus，审查用 Sonnet，轻量用 Haiku |
| 随意设置任意数量终端实例 | 并行化过度，工作区混乱 | 合并冲突风险高，管理成本大 | 最小可行并行化，真正需要时才增加实例 |
| 多个 Claude 实例处理重叠代码工作不使用 git 工作树 | 并行修改冲突 | 覆盖他人更改，代码丢失 | 用 git worktree 隔离并行工作，每个工作树独立分支 |
| 跳过阶段直接进入实现 | 没有规划直接编码 | 方向错误，返工成本高 | 顺序执行各阶段：探索→计划→实现→审查→验证 |
| 子代理返回不验证就直接接受 | 盲目信任子代理输出 | 错误累积，问题发现晚 | 迭代检索，最多3轮追问确保质量 |
| 不给子代理传递目标上下文只传递查询 | 子代理缺乏全局视角 | 输出偏离实际需求 | 给子代理传递完整目标上下文，不只是查询 |
| 不投资构建可复用模式，每次从头开始 | 不积累资产 | 长期效率低下 | 构建可复用模式（子代理、技能、命令、规划模式），产生复合收益 |
