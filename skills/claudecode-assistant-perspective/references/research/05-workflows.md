## 一、顺序多代理编排工作流

### Phase 1 探索
- **输入**: 用户需求描述、代码库现状、相关文档
- **目标**: 全面理解问题域、识别风险、识别可复用资产、明确约束条件
- **Agent 选择**: 
  - code-explorer - 代码库探索与理解
  - architect - 架构影响评估
  - search-first - 查找现有实现和模式
- **输出**: 问题分析报告、可复用资产清单、风险评估、需求澄清清单
- **质量门限**: 
  - 80% 的相关代码文件已被审阅
  - 所有外部依赖已识别
  - 风险等级已明确标注

### Phase 2 计划
- **输入**: 探索阶段输出、用户确认的需求
- **目标**: 制定详细实施计划、分解任务、确定优先级
- **Agent 选择**:
  - planner - 实施规划专家
  - code-architect - 架构设计
  - type-design-analyzer - 类型与接口设计
- **输出**: 详细任务分解、里程碑、验收标准、技术选型方案
- **质量门限**:
  - 任务粒度 < 4 小时
  - 依赖关系清晰
  - 回滚方案已准备

### Phase 3 实现
- **输入**: 计划阶段输出
- **目标**: 按照 TDD 流程实现功能
- **Agent 选择**:
  - tdd-guide - TDD 流程引导
  - feature-dev - 功能开发
  - code-simplifier - 代码简化与重构
- **输出**: 可运行代码、单元测试、集成测试
- **质量门限**:
  - 测试覆盖率 >= 80%
  - 所有测试通过
  - 代码符合编码规范

### Phase 4 审查
- **输入**: 实现阶段输出
- **目标**: 质量保证、安全审计、性能评估
- **Agent 选择**:
  - code-reviewer - 代码质量审查
  - security-reviewer - 安全审计
  - comment-analyzer - 注释与文档审查
  - pr-test-analyzer - PR 测试分析
- **输出**: 审查报告、问题清单、改进建议
- **质量门限**:
  - 无 CRITICAL 级别问题
  - HIGH 级别问题 <= 2 个
  - 所有安全检查通过

### Phase 5 验证
- **输入**: 审查阶段输出、修复后的代码
- **目标**: 最终验证、文档更新、知识捕获
- **Agent 选择**:
  - silent-failure-hunter - 静默失败检测
  - verification-loop - 验证循环
  - doc-updater - 文档更新
- **输出**: 验证报告、更新的文档、提交准备
- **质量门限**:
  - 端到端测试通过
  - 文档与代码同步
  - 回归测试无失败

## 四、问题诊断工作流

### 1. 问题分类
- **类型识别**:
  - 构建错误 / 测试失败
  - 性能问题 / 安全漏洞
  - 功能异常 / 集成问题
  - 配置问题 / 环境问题
  - 权限问题 / 工具故障
- **严重程度分级**:
  - CRITICAL - 阻塞开发/发布
  - HIGH - 影响核心功能
  - MEDIUM - 影响次要功能
  - LOW -  cosmetic/建议改进
- **影响范围评估**:
  - 单文件 / 单模块
  - 跨模块 / 全系统

### 2. 信息收集
**收集清单**:
- [ ] 错误消息完整收集
- [ ] 复现步骤记录
- [ ] 相关代码变更历史
- [ ] 环境信息（OS, 版本, 依赖）
- [ ] 相关日志文件
- [ ] 类似问题历史记录
- [ ] 用户报告和影响评估

### 3. 假设验证
**验证方法**:
- **二分法**: 逐步缩小问题范围
- **控制变量法**: 逐个变更一个变量
- **回归测试**: 验证修复是否引入新问题
- **对比法**: 与正常工作版本对比
- **隔离测试**: 在隔离环境复现

### 4. 根因分析
**分析技术**:
- 5 Whys 层层追问
- 鱼骨图因果分析
- 依赖链追踪
- 代码审查确认
- 专家咨询（调用栈分析
- 状态变化追踪

### 5. 修复方案
**方案要素**:
- 最小侵入原则
- 回归测试覆盖
- 兼容性保证
- 性能影响评估
- 回滚方案准备
- 受影响模块清单
- 验证步骤定义

### 6. 预防措施
**预防清单**:
- [ ] 添加回归测试
- [ ] 更新文档和注释
- [ ] 提取为 Skill/Agent 知识
- [ ] 更新编码规范
- [ ] 添加 Hook 自动化检查
- [ ] 记录到知识库
- [ ] 分享给团队

## 五、Git 工作树并行工作流

### 1. 主分支稳定
**前置条件**:
- [ ] main 分支 CI 全绿
- [ ] 所有测试通过（100%
- [ ] 无未解决的冲突
- [ ] 最新代码已拉取
- [ ] 工作区干净
- [ ] 锁定状态确认

### 2. 创建工作树
**步骤**:
```bash
# 创建新的工作树
git worktree add ../feature-branch
# 或者创建并切换到新分支
git worktree add -b feature-name ../feature-name main
# 列出所有工作树
git worktree list
# 验证工作树状态
cd ../feature-branch && git status
```
**检查清单**:
- [ ] 工作树路径合理组织
- [ ] 分支命名规范（feature/fix/refactor/docs 前缀
- [ ] 工作树隔离
- [ ] 独立依赖安装
- [ ] 独立测试数据库实例
- [ ] 端口冲突避免

### 3. 并行开发
**最佳实践**:
- 每个工作树独立开发一个功能
- 定期从 main 同步变更
- 工作树间共享 git 状态独立
- 避免跨工作树文件修改
- 使用独立的 node_modules 缓存
- 独立的测试环境隔离

### 4. 独立测试
**检查清单**:
- [ ] 每个工作树独立运行测试
- [ ] 不影响其他工作树
- [ ] 数据库实例隔离
- [ ] 端口配置独立
- [ ] 构建产物隔离
- [ ] 覆盖率达标（80%+
- [ ] 所有测试通过

### 5. 合并审查
**合并流程:
1. 工作树内完成功能完成开发和测试
2. 推送分支推送到远程
3. 创建 PR
4. 代码审查
5. 合并到 main
6. 清理工作树
```bash
# 清理工作树
git worktree remove ../feature-branch
# 或保留分支清理
git worktree prune
```

## 六、检查点设计模式

### 质量门限定义
**门限类型**:
- **测试覆盖率门限: 单元测试 >= 80%
- **安全检查门限: 无 CRITICAL 安全问题
- **性能门限: 响应时间 < 200ms（hooks）
- **代码质量门限: 无 lint 错误
- **构建门限: 构建成功无警告
- **文档门限: 关键变更有文档同步

### 通过/失败标准
**标准定义**:
- **明确的量化指标，非主观判断
- 可自动化测量
- 有明确的阈值
- 有异常处理流程
- 失败时的 escalation 路径
- 重新评估机制

### 自动评估脚本
**实现模式**:
- Node.js 脚本（scripts/*.js）
- 集成到 PreToolUse/PostToolUse hooks
- 异步 hooks 超时 <= 30s
- 阻塞 hooks 快速（< 200ms）
- 非关键错误 exit 0（不阻塞执行
- 结构化 JSON 输入输出
- stderr 日志前缀 [HookName]

**示例结构**:
```javascript
// scripts/hooks/quality-check.js
module.exports = {
  name: 'quality-check',
  run: async (input) => {
    const results = {
    pass: true/false,
    issues: [],
    metrics: {}
    }
    // 检查逻辑
    return results
  }
}
```

### 回滚机制
**回滚策略**:
- **自动回滚**: 关键检查失败时自动回滚
- **手动回滚**: 用户确认后回滚
- **部分回滚**: 只回滚有问题的部分
- **Git 重置**: git reset --hard
- **配置还原**: 备份和还原
- **数据恢复**: 数据库回滚

**回滚步骤**:
1. 检测到失败条件
2. 触发回滚流程
3. 执行回滚操作
4. 验证回滚结果
5. 记录回滚日志
6. 通知相关人员
