# 04 - 最佳实践指南
---

## 一、上下文管理最佳实践

### 1. 策略性清理 vs 自动压缩
- **策略性清理**：制定计划后，使用 `/clear` 清除积累的探索上下文，仅保留执行相关内容
- **手动压缩**：禁用自动压缩，在逻辑间隔点手动执行压缩
- **压缩时机**：上下文使用率达到 ~50% 时进行手动压缩
- **技能辅助**：创建自定义技能来执行上下文压缩，控制压缩粒度

### 2. 跨会话持久化方法
- **会话存储文件**：每个会话创建独立的 `.tmp` 文件，保存：
  - 已验证有效的方法（带证据）
  - 已尝试但无效的方法
  - 尚未尝试的方法和待办事项
- **次日恢复**：新会话开始时，直接提供前一天会话文件路径
- **文件组织**：按会话日期隔离存储，避免新旧上下文污染

### 3. 动态上下文注入技术
- **CLI 标志注入**：使用 `--system-prompt` 标志动态加载上下文
  ```bash
  claude --system-prompt "$(cat memory.md)"
  ```
- **角色化别名**：为不同工作模式创建专用别名
  - `claude-dev`：日常开发模式
  - `claude-review`：代码审查模式
  - `claude-research`：研究探索模式
- **优先级**：系统提示 > 用户消息 > 工具结果

### 4. 钩子辅助持久化
- **PreCompact 钩子**：上下文压缩前，保存重要状态到文件
- **Stop/SessionEnd 钩子**：会话结束时，自动持久化学到的知识
- **SessionStart 钩子**：新会话开始时，自动加载之前的上下文
- **轻量设计**：使用 Stop 钩子而非 UserPromptSubmit，避免每条消息都增加延迟

## 二、Token 经济学

### 1. 模型选择决策树

| 任务类型 | 推荐模型 | 选择理由 |
|---------|---------|---------|
| 探索/搜索 | Haiku | 快速、便宜，找文件足够 |
| 简单编辑 | Haiku | 单文件改动，指令清晰 |
| 多文件实现 | Sonnet | 编码最佳平衡 |
| 复杂架构 | Opus | 需要深度推理 |
| PR 审查 | Sonnet | 理解上下文，捕捉细微差别 |
| 安全分析 | Opus | 不能遗漏漏洞 |
| 文档编写 | Haiku | 结构简单 |
| 复杂调试 | Opus | 需要在脑海中保存整个系统 |

**决策原则**：
- 90% 编码任务默认使用 Sonnet
- 升级到 Opus 的触发条件：
  - 首次尝试失败
  - 任务涉及 5+ 个文件
  - 架构决策
  - 安全关键代码

### 2. 子代理架构优化
- **子代理上下文问题**：协调器有语义上下文，子代理只有字面查询
- **迭代检索模式**：
  1. 协调器评估每个子代理返回结果
  2. 在接受前提出后续问题
  3. 子代理返回源并获取答案
  4. 循环直到满足（最多 3 轮）
- **关键**：传递目标上下文，而非仅传递查询

**顺序阶段协调器**：
```
阶段 1：研究 → research-summary.md
阶段 2：计划 → plan.md
阶段 3：实现 → 代码变更
阶段 4：审查 → review-comments.md
阶段 5：验证 → 完成或循环
```
- 每个代理一个明确输入，一个明确输出
- 输出成为下一阶段输入
- 不跳过阶段
- 代理间使用 `/clear`
- 中间结果存储为文件

### 3. 中间结果文件存储
- **模式**：将每个阶段的输出保存为独立文件
- **好处**：
  - 减少子代理间的上下文传递
  - 可回溯检查每个阶段的质量
  - 支持断点续做
- **格式**：Markdown 文件，清晰的章节结构

### 4. 成本优化检查清单
- [ ] 用 CLI + 技能替代常驻 MCP（如 GitHub、Supabase）
- [ ] 使用 mgrep 替代 grep（平均减少 ~50% token）
- [ ] 代码库模块化：单文件数百行而非数千行
- [ ] 子代理使用最便宜的足够模型
- [ ] 中间结果文件化而非上下文传递
- [ ] 手动压缩而非自动压缩（控制压缩时机）

## 三、并行化最佳实践

### 1. 最小可行并行化原则
- **核心原则**：以最少的并行量完成最多的工作
- **避免**：设置任意的终端数量（如"运行 5 个本地 + 5 个上游"）
- **添加终端的条件**：真正的必要性，而非随意增加
- **级联方法**：
  - 右侧打开新任务标签
  - 从左到右清扫，从旧到新
  - 一次最多专注 3-4 个任务

### 2. Git 工作树模式
- **适用场景**：多个 Claude 实例处理重叠代码
- **命令示例**：
  ```bash
  git worktree add ../project-feature-a feature-a
  git worktree add ../project-feature-b feature-b
  git worktree add ../project-refactor refactor-branch
  ```
- **配套措施**：
  - 每个工作树对应一个 Claude 实例
  - 使用 `/rename <name>` 命名所有聊天
  - 为每个实例制定明确定义的计划

### 3. 多实例任务划分
- **推荐模式**：
  - 主聊天：代码变更
  - 分叉聊天：关于代码库当前状态的问题或外部服务研究
- **双实例启动模式**：
  - **实例 1（脚手架代理）**：搭建项目结构、创建配置
  - **实例 2（深度研究代理）**：连接服务、创建 PRD、绘制架构图、编译参考

### 4. 避免重叠冲突
- **边界清晰**：确保分叉和原始会话的操作范围定义良好
- **最小重叠**：代码变更的重叠范围尽可能小
- **工作树强制**：扩展实例且代码重叠时，必须使用 git worktrees

## 四、持续学习机制

### 1. Stop 钩子学习流程
- **设计决策**：使用 Stop 钩子而非 UserPromptSubmit
  - UserPromptSubmit：每条消息运行 → 增加每个提示的延迟
  - Stop：会话结束时运行一次 → 轻量级，不影响会话速度
- **学习流程**：
  1. 会话结束触发 Stop 钩子
  2. 提取非平凡的发现（调试技术、变通方法、项目特定模式）
  3. 将知识保存为新技能
  4. 下次遇到类似问题时自动加载技能

### 2. 可复用模式积累
- **投资方向**：
  - 子代理
  - 技能
  - 命令
  - 规划模式
  - MCP 工具
  - 上下文工程模式
- **复利效应**：前期构建繁琐，但随着模型和代理框架改进效果呈指数级增长

### 3. 复利效应设计
- **模式识别**：重复遇到相同问题或得到相同回答时，必须追加到技能
- **问题**：浪费 token、浪费上下文、浪费时间
- **解决方案**：发现非平凡知识 → 保存为技能 → 下次自动加载

### 4. 技能迭代方法
- **基准测试工作流**：
  1. 分叉对话
  2. 在一个分叉中不使用技能启动新工作树
  3. 结束时对比差异
  4. 查看日志记录
- **评估模式类型**：
  - **检查点评估**：设置明确检查点，按定义标准验证
  - **持续评估**：每 N 分钟或重大变更后运行，完整测试 + lint

## 五、按场景的最佳实践表

| 场景 | 核心原则 | 具体做法 | 反模式 |
|------|---------|---------|--------|
| **功能开发** | TDD + 分阶段 + 可验证 | 1. 先写测试再实现<br>2. 使用规划模式先定计划<br>3. 子代理分阶段执行<br>4. 每个阶段输出文件化 | 跳过规划直接编码<br>不写测试直接实现<br>所有工作在单一上下文中完成 |
| **代码审查** | 上下文充足 + 模型合适 | 1. 使用 Sonnet 级别模型<br>2. 提供完整 git diff 上下文<br>3. 安全关键代码升级到 Opus<br>4. 审查后输出到审查文件 | 使用 Haiku 做审查<br>只提供部分代码片段<br>审查结果不持久化<br>跳过安全检查 |
| **调试问题** | 全系统视角 + 迭代验证 | 1. 复杂 bug 使用 Opus<br>2. 提供完整系统上下文<br>3. 每次尝试后验证结果<br>4. 将有效调试方法存为技能 | 盲目猜测原因<br>不验证修复效果<br>调试知识不积累<br>上下文不足时强行调试 |
| **长期会话** | 定期持久化 + 上下文管理 | 1. 每会话创建状态总结文件<br>2. ~50% 上下文时手动压缩<br>3. 无用上下文及时 `/clear`<br>4. 会话结束用 Stop 钩子保存学习 | 依赖自动压缩<br>上下文满了才处理<br>会话间无衔接<br>学到的模式不沉淀 |
