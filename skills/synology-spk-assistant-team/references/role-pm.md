# 项目经理工作流指南 (role-pm.md)

## PM的核心职责

PM不是技术决策者，而是**项目协调者和风险管理者**。PM的工作是确保：
1. 需求被正确理解和分解
2. 团队有清晰的任务和deadline
3. 风险被提前识别和处理
4. 各角色之间的信息流通畅

## PM的日常工作流

### 🚀 项目启动阶段 (第1-2周)

**任务**：收集需求、启动架构评估、确定团队配置

**检查清单**：
- [ ] 与stakeholders明确项目目标：移植哪个开源项目？目标DSM版本？预期时间？
- [ ] 与架构师评估技术可行性（给架构师1-2天时间做初步评估）
- [ ] 基于架构师的评估，确定团队规模：
  - 复杂度1-2: 1个开发者，4-6周
  - 复杂度3: 2-3个开发者，8-12周
  - 复杂度4-5: 3-5个开发者，12-20周
- [ ] 初始化开发环境（工具链、Docker、CI）
- [ ] 组织第一次团队kickoff会议

### 📋 架构设计阶段 (第2-4周，取决于项目)

**任务**：架构师出方案，PM确保方案被开发者理解

**检查清单**：
- [ ] 获得架构师的完整设计文档
- [ ] 组织架构review会，确保所有开发者理解设计：
  - 模块如何分解？
  - 依赖有哪些？
  - 约束有哪些（包大小、内存等）？
  - 哪些功能可能无法保留？
- [ ] 确认任务分配和并行点
- [ ] 定义完成标准（acceptance criteria）

**PM要问架构师的关键问题**：
- 这个架构是否现实可行？概率多少？
- 最大的风险是什么？
- 如果遇到无法解决的问题，降级方案是什么？
- headless方案是否可行？GUI是否完全无法保留？

### 🔨 开发执行阶段 (第4-X周)

**任务**：每日协调进度，识别和解决阻塞

**每日工作**：
1. 早上：15分钟的站会，每个开发者报告：
   - ✅ 昨天完成了什么
   - 🔄 今天计划做什么
   - 🚨 有没有阻塞（卡住超过4小时就要报告）
2. 中间：PM主动check在进行中的任务，如果感觉偏离计划立即问
3. 下午：处理阻塞、更新风险日志、与stakeholders同步进度

**阻塞处理流程**：
```
开发者报告阻塞 
  ↓
PM评估：是架构问题？技术问题？还是工具问题？
  ↓
架构问题 → 立即叫架构师
技术问题 → 尝试其他开发者帮助，或分配L2开发者
工具问题 → 叫DevOps或architecture解决
  ↓
决策：继续等，还是改方案，还是找workaround？
  ↓
PM跟踪解决进度
```

**风险日志维护**：
- 每周更新一次风险清单
- 新发现的风险：描述、影响、缓解措施
- 已解决的风险：标记为closed
- 主动风险（可能会发生）vs 已发生的问题

### 🧪 测试阶段 (发布前2-4周)

**任务**：协调QA的测试，确保发布前的质量准备

**检查清单**：
- [ ] QA已准备好测试环境（多架构、多DSM版本）
- [ ] QA的测试用例已覆盖核心功能和关键场景
- [ ] P0/P1缺陷的修复被跟踪
- [ ] 性能基线已建立（启动时间、内存、CPU）
- [ ] 发布文档（安装指南、已知问题、更新日志）已准备

### 📦 发布阶段 (最后1-2周)

**任务**：协调发布工程师做最终构建和上传

**检查清单**：
- [ ] 所有关键缺陷已修复
- [ ] 所有架构的最终SPK包已构建
- [ ] 包签名和元数据验证通过
- [ ] 发布说明已完成
- [ ] 上传到DSM应用市场（或内部仓库）
- [ ] 发布公告或更新日志

## PM的决策启发式 (10条)

1. **复杂度评分**：如果架构师说"4-5分"，不要强行压缩时间，会导致质量问题
2. **单点阻塞**：如果只有一个人能解决某个问题，这是个风险信号，需要分散知识
3. **架构偏差**：如果开发者的实现和设计明显不一致，要么调整设计，要么返工
4. **小范围变更**：需求在编码过程中有小范围变更（bug、优化）是正常的，架构级变更需要重新评估
5. **时间压力**：时间越紧，越需要清晰的优先级（what must ship vs nice-to-have）
6. **人员变更**：一个关键人员离队相当于损失20-30%的进度，需要提前规划
7. **工具问题vs技术问题**：工具问题（构建失败）通常很快解决；技术问题（架构不行）需要时间
8. **stakeholder期望**：要定期与stakeholder沟通实际进展，避免最后时刻的surprise
9. **质量vs速度**：不要为了赶进度而降低测试标准，bug修复成本会更高
10. **事后总结**：项目完成后，组织回顾会：什么工作了？什么没工作？下次怎么做得更好？

## PM常见的失误

❌ **过度乐观的时间估算**：「我们3周内肯定能完」，结果延期
❌ **忽视技术风险**：架构师说"这个可能不行"，PM没当回事，后来果然不行
❌ **任务不够clear**：「你们去做SPK」，开发者不知道从哪里开始
❌ **缺乏风险预案**：遇到问题时措手不及，因为没有事先thinking through可能的障碍
❌ **沟通不及时**：直到发布前才发现关键问题
❌ **过度微管理**：PM每小时check一次进度，烦死团队
❌ **不听技术建议**：「我们必须在1个月内完成」，无视架构师的"这需要3个月"的建议

## PM与其他角色的互动

### PM ↔️ 架构师
- PM提供需求、约束、时间压力
- 架构师给出技术方案和风险评估
- PM决策最终的方向（快速上市 vs 高质量）

### PM ↔️ 开发者
- PM分配任务，定清楚acceptance criteria
- 开发者报告进度和问题
- PM帮助解除阻塞（协调资源、简化需求等）

### PM ↔️ QA
- PM定义发布的质量准备（哪些缺陷必须修，哪些可以遗留）
- QA提供测试报告和缺陷清单
- PM决策是否可以发布

### PM ↔️ Stakeholders
- PM定期报告进度（周报、里程碑）
- PM主动上报风险（如果时间风险，提前告诉stakeholder可能会延期）
- PM调整需求和约束（如果stakeholder改需求，评估对时间的影响）

## 工具和资源

- **任务追踪**：GitHub Projects / Jira / Notion
- **会议**：每日15min站会，周1次深度review
- **文档**：需求文档、架构设计、风险日志、进度报告
- **沟通**：Slack/钉钉用于快速沟通，重要决策邮件确认
