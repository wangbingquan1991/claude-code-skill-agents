# QA测试策略 (role-qa.md)

## QA的核心职责

QA不是bug finding service，而是**质量保证的设计者和执行者**。QA要确保SPK在多个DSM版本、多个架构上都能工作。

## 测试金字塔

```
        ▲
       / \  E2E测试 (发布前)
      /   \
     / --- \ 集成测试 (多架构)
    /       \
   / ------- \ 功能测试 (功能完整性)
  /           \
 / ----------- \ 单元测试 (开发者负责，QA验证)
```

- **单元测试** (开发者): 单个函数的正确性
- **功能测试** (QA): 整个功能的完整性
- **集成测试** (QA): 多个功能之间的交互
- **E2E测试** (QA): 真实DSM环境下的端到端流程

## 测试矩阵

### 强制测试矩阵 (必须覆盖)
```
            DSM 7.2    DSM 7.1
x64         ✅         ✅
ARM64       ✅         ✅
x86         ✅         ❌ (可选)
```

- 每个(DSM版本 × 架构)组合都要部署一个测试环境
- 最少3个并行的测试环境，一个做功能测试，一个做长时间运行测试，一个做压力测试

### 可选测试矩阵 (如有时间)
```
DSM 6.2 (遗留支持，如果需要)
```

## QA的工作流

### 📋 测试计划阶段 (架构设计完成)

1. **定义测试场景**：
   - 启动应用 (正常启动、异常启动、重启后)
   - 核心功能 (根据项目特性列出关键功能)
   - 长时间运行 (24h+稳定性)
   - 边界case (超大文件、极限负载)
   - 与其他SPK共存 (会不会冲突)

2. **建立测试环境**：
   ```bash
   # 为每个(DSM版本 × 架构)部署一个Docker容器
   docker run -it --name dsm-7.2-x64 synology/dsm:7.2 /bin/bash
   docker run -it --name dsm-7.2-arm64 synology/dsm:7.2 /bin/bash
   # ...
   ```

3. **准备测试工具**：
   - SSH连接到DSM环境
   - 日志收集脚本 (dmesg, syslog等)
   - 性能监控脚本 (top, iostat等)
   - 缺陷追踪 (Jira, GitHub Issues等)

### ✅ 功能测试阶段 (核心功能完成)

**测试流程**：
1. 接收开发者提交的SPK包
2. 在所有(DSM版本 × 架构)上安装SPK
3. 执行测试用例，记录结果
4. 发现问题 → 分类优先级 → 上报给开发者

**测试用例模板**：
```markdown
# 测试用例: 启动vscode应用

## 前置条件
- DSM 7.2已安装
- vscode SPK已上传

## 测试步骤
1. 在DSM应用市场找到vscode
2. 点击安装
3. 等待安装完成
4. 点击打开

## 预期结果
- [ ] 应用在10秒内启动
- [ ] 看到vscode的UI
- [ ] 可以新建文件和打开已有文件

## 实际结果
[记录实际发生了什么]

## 缺陷
如果有问题，记录为缺陷
```

### 🔄 兼容性测试 (多版本多架构)

运行同样的测试用例在不同的环境上，确保没有环境相关的bug：

```bash
# 对于每个(DSM版本 × 架构)组合
for env in dsm-7.2-x64 dsm-7.2-arm64 dsm-7.1-x64; do
  echo "Testing on $env"
  ssh root@$env "install-spk && test-core-function"
done
```

### 📊 性能基线测试

建立性能基线，后续版本对标此基线：

```bash
# 启动时间
time spkcli start vscode

# 内存占用
ssh dsm "top -b -n 1 | grep vscode"

# 包大小
ls -lh packages/vscode*.spk

# 构建时间
time make arch-x64
```

**基线目标** (例子):
- 启动时间: <10秒
- 内存占用: <200MB
- 包大小: <800MB

### 🚨 缺陷管理

#### 缺陷优先级分类

| 优先级 | 定义 | 例子 | 发布策略 |
|--------|------|------|---------|
| P0 (Critical) | 功能完全不可用或数据丢失 | 应用崩溃、无法启动、文件损坏 | ❌ 必须修复才能发布 |
| P1 (High) | 核心功能受影响或严重降级 | 性能极差、关键按钮无响应 | ⚠️ 强烈建议修复 |
| P2 (Medium) | 次要功能有问题但不影响使用 | UI排版错误、某个高级功能bug | ⏳ 可在下个版本修复 |
| P3 (Low) | 极少数情况下的轻微问题 | 少见的UI抖动、文档错误 | 📝 Nice-to-fix |

#### 缺陷报告流程
```
发现问题 
  ↓
分类优先级 (P0-P3)
  ↓
撰写缺陷报告 (用缺陷报告模板)
  ↓
上报给PM/开发者
  ↓
开发者修复
  ↓
QA验证修复 (Re-test)
  ↓
标记为closed
```

**缺陷报告模板**：
```markdown
# 缺陷: vscode启动时经常崩溃

## 优先级
P0 (Critical)

## 环境
- DSM版本: 7.2
- 架构: x64
- SPK版本: 1.0.0-alpha.1

## 复现步骤
1. 在DSM应用市场安装vscode
2. 点击打开应用
3. 应用在加载界面崩溃

## 预期vs实际
- 预期: 应用正常启动
- 实际: 应用崩溃，错误代码: SIGSEGV

## 日志
[粘贴相关的错误日志]

## 影响范围
- [ ] DSM 7.2 x64: 100%复现
- [ ] DSM 7.2 ARM64: [未测]
- [ ] DSM 7.1: [未测]
```

### 📈 长时间运行测试 (24h+)

启动SPK后让它运行24小时，监控是否有内存泄漏、CPU升高等问题：

```bash
# 启动应用
ssh dsm "spkcli start vscode"

# 每小时记录一次内存和CPU
for i in {1..24}; do
  ssh dsm "top -b -n 1 | grep vscode" >> perf_log.txt
  sleep 3600
done

# 分析日志，看看内存是否在持续升高
```

### 🎯 发布前检查清单

发布前，QA要确认：

- [ ] 所有P0缺陷已修复
- [ ] 所有强制测试矩阵(DSM 7.2 x64/ARM64/x86)已通过
- [ ] 性能基线已建立和验证
- [ ] 长时间运行测试已完成，无内存泄漏
- [ ] 已在真实DSM环境(不是容器)上验证过 (最好由用户或PM验证)

## QA常见的错误

❌ **被动测试**：只等开发者说"可以测试了"再开始  
✅ **主动参与**：从架构设计阶段就参与，设计测试计划

❌ **只测试happy path**：只测正常流程，不测异常情况  
✅ **全面测试**：正常case + 边界case + 压力测试

❌ **环境单一**：只在一个环境测试  
✅ **多环境**：至少DSM 7.2 x64/ARM64/x86都测

❌ **缺陷分类不清**：所有问题都报P0  
✅ **合理分类**：只有严重问题才是P0

❌ **不记录测试结果**：凭记忆**很容易忘  
✅ **完整文档**：每个测试都有记录
