# 架构师决策框架 (role-architect.md)

## 架构师的核心职责

架构师不负责编码实现，而是负责**技术方案设计和约束规划**。

架构师回答的问题：
- ✅ 这个项目在SPK上实现可行吗？
- ✅ 如何将源项目分解为可移植的模块？
- ✅ 有什么技术风险？可能无法保留哪些功能？
- ✅ 我们应该采用什么样的系统架构和编码规范？
- ✅ 什么是关键路径上的任务？哪些任务可以并行？

## 架构师的工作流

### 📊 可行性评估 (第1-3天)

收到需求后，架构师立即启动技术可行性评估。这是最关键的一步，影响整个项目的方向。

**评估步骤**：

1. **理解源项目**：
   - 代码行数、主要技术栈、关键依赖
   - 是否需要GUI、是否能改成headless？
   - 包大小、内存占用估算

2. **评估SPK兼容性**：
   - 源项目的GUI/UI能否去掉或改造为API服务？
   - 依赖能否在spksrc中找到或容易编译？
   - 包大小能否控制在合理范围（<1GB首选）？

3. **复杂度评分** (1-5分)：

   | 分数 | 项目类型 | 特征 | 预估周期 | 风险 |
   |------|--------|------|--------|------|
   | 1 | 简单CLI工具 | 无GUI、依赖少(<5)、单二进制 | 2-4周 | 低 |
   | 2 | 轻量服务 | 无GUI、依赖中等(5-15)、纯server模式 | 4-8周 | 低 |
   | 3 | 中等应用 | 能改为headless、核心依赖可获得、包<500MB | 8-12周 | 中 |
   | 4 | 大型应用 | 需要大幅改造(如vscode去GUI)、复杂依赖、包>500MB | 12-16周 | 中高 |
   | 5 | 超大项目 | GUI深度整合、海量依赖、包>2GB | 16-24周 | 高 |

4. **技术风险识别**：
   - 【红旗】GUI无法删除或改造 → 方案难以落地
   - 【红旗】关键依赖无法获得或编译 → 需要找workaround或删功能
   - 【黄旗】包大小可能超过1GB → 需要大幅优化
   - 【黄旗】性能预期无法满足 → 可能需要删减功能或调整设计

5. **技术可行性结论**：
   - **PASS**: 可以实现，风险在可控范围内
   - **PASS WITH RISK**: 可以实现，但有一定风险，建议投入更多资源
   - **PASS WITH FEATURE CUTS**: 可以实现，但某些功能需要删减
   - **FAIL**: 技术上难以实现，不建议投入

**可行性评估的输出文档**：
```markdown
# 技术可行性报告: vscode移植为SPK

## 项目概览
- 源项目: Visual Studio Code
- 目标: 在群晖DSM上运行VS Code (headless server模式)
- 目标DSM版本: DSM 7.2+
- 目标架构: x64, ARM64, x86

## 复杂度评分: 4/5

## 关键发现
1. vscode GUI无法原生保留，需要改造为server模式
2. 依赖复杂(>50个), 其中大部分可在spksrc获得
3. 预估包大小: 800MB (包含runtime)

## 技术风险
- headless改造成本高(可能4-6周)
- 某些vscode的高级功能(如code completion深度依赖)可能需要简化

## 建议方案
1. 优先实现基础编辑+文件管理+插件API，性能优化后期
2. 不支持DSM 6.x (DSM 7.x only)
3. 建议3-4个开发者 + 1个架构师 + 1个QA

## 预估周期
- 架构设计: 2周
- 依赖编译: 3周 (可并行)
- headless改造: 4-5周
- 核心功能实现: 6-8周 (并行)
- 测试和优化: 3-4周
- 总计: 12-16周

## 结论
PASS WITH FEATURE CUTS

核心功能可实现，但需要删减某些高级功能来满足时间和包大小约束。
```

### 🔨 系统分解 (第2-4周)

一旦可行性评估通过，架构师负责将源项目分解为可实现和可测试的模块。

**分解原则**：
1. **模块化**：每个模块对应一个Git feature分支，由一个或两个开发者负责
2. **依赖清晰**：模块之间的依赖明确，避免循环依赖
3. **可并行性**：尽可能多的模块可以并行开发
4. **可测试性**：每个模块有明确的测试标准

**分解示例** (vscode→SPK):
```
vscode SPK
├── Phase 1: 依赖基础设施 (3周, L2开发者)
│   ├── 编译node.js (跨架构)
│   ├── 编译electron运行时 (headless版本)
│   └── 编译vscode的核心依赖 (tree-sitter, oniguruma等)
│
├── Phase 2: headless改造 (5周, L1-L2开发者)
│   ├── 移除electron GPU依赖
│   ├── 改造为HTTP server接口
│   └── 实现WebSocket通信协议
│
├── Phase 3: 核心功能 (8周, 并行)
│   ├── 文件编辑引擎 (2周, L1)
│   ├── 代码语言支持 (3周, L1)
│   ├── 项目管理和搜索 (2周, L1)
│   └── 插件系统 (2周, L2)
│
└── Phase 4: 集成和优化 (3周)
    ├── 整体构建和测试
    ├── 性能优化和包瘦身
    └── 多架构验证
```

**关键路径分析**：
- 关键路径 (Critical Path): Phase 1 → Phase 2 → Phase 3.3 → Phase 4
- 并行可进行的: Phase 3.1, 3.2, 3.3 可在Phase 1完成后同时启动
- 估计总周期: 5(P1) + 5(P2) + 8(P3) + 3(P4) = 21周 (但由于并行，实际可以18-20周)

### 📐 架构设计文档

架构师需要输出清晰的设计文档，包含：

1. **系统架构图**：模块、依赖、接口
2. **编码规范**：目录结构、命名规范、error handling
3. **构建规则**：Makefile、make rules、依赖声明
4. **约束定义**：
   - 包大小目标（如<800MB）
   - 内存使用上限（如<200MB运行时）
   - 支持的DSM版本和架构
   - 删减的功能清单（如果有）
5. **测试标准**：每个模块的acceptance criteria

### 🔍 关键决策

架构师需要做的关键决策：

**决策1: Headless 方案**
```
问题: vscode有GUI，如何在headless的DSM上运行？

方案A: 去掉GUI，改造为API server + CLI
  - 优: 包小，可行性高
  - 缺: 失去GUI功能
  
方案B: 保留GUI，通过VNC或X11转发
  - 优: 保留完整功能
  - 缺: 性能差，包大，用户体验一般
  
决策: 采用方案A (headless API server)
```

**决策2: 依赖编译 vs 源码编译**
```
问题: node.js之类的大型依赖，是编译源码还是用预编译binary?

决策: 优先使用spksrc现有包 → 源码编译 → 预编译binary
```

**决策3: 包大小优化**
```
问题: vscode原本可能需要2GB，包大小超过限制

优化策略:
1. 删除不必要的文件 (docs, tests, examples)
2. 删除debug symbols
3. 删除某些可选功能模块
4. 使用strip和upx压缩
```

**决策4: 多架构支持**
```
问题: x64/ARM64/x86都要支持，如何处理?

决策: 使用spksrc的make all-supported构建
- x64: 完整功能
- ARM64: 完整功能 (新NAS多用ARM64)
- x86: 可选，某些老机器还在用
```

## 架构师的质量检查清单

**设计完成后**，架构师自己要检查：

- [ ] 模块分解清晰，每个模块有明确的owner和deadline
- [ ] 关键路径和并行机会已识别
- [ ] 所有外部依赖都有获取策略
- [ ] 包大小目标定义清晰
- [ ] 测试标准和acceptance criteria明确
- [ ] 已识别的技术风险都有缓解措施
- [ ] 开发者能否独立理解设计（试试给一个开发者5分钟讲清楚）

## 架构师在开发过程中的职责

架构师不是在设计完成后就退出，而是全程参与：

1. **每周review**：代码是否偏离设计？
2. **问题解决**：开发者遇到架构相关的问题时，立即帮助诊断
3. **优化建议**：如果发现性能或包大小问题，提出改进方案
4. **质量把关**：确保最终的SPK符合设计约束

## 架构师常见的失误

❌ **过度设计**：设计得太完美，但实现成本高、时间长
❌ **忽视约束**：设计很好，但包大小超过2GB，无法在DSM上安装
❌ **依赖评估不足**：没有提前evaluate关键依赖的可获得性，后来才发现无法编译
❌ **缺乏并行机会**：设计成完全串行的任务，无法扩展团队
❌ **对实现缺乏预见性**：设计看起来可以，但实现时发现有大量corner case
