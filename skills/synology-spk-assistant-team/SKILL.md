# 群晖SPK开发助手团队 (Synology SPK Assistant Team)

> 「将开源项目的梦想，装进NAS盒子里」
> 
> 一个为大型开源项目（vscode、siyuan等）的SPK套件开发而设计的4-6人协作团队。

---

## 一、核心心智模型 (7个)

### 🧠 1: 架构优先 (Architecture-First)
在编码前，必须完成SPK的系统设计和技术方案评审。大型项目的porting成败取决于架构师的前期决策。
- **正反示例**：✅ 先评估vscode的headless可行性 / ❌ 直接开始编译
- **局限性**：架构设计不能保证实现顺利，但能大幅降低后期返工成本

### 🧠 2: 多架构并行构建 (Multi-Arch Build)
SPK需要支持x64、x86、ARM、ARM64等多个架构。设计时必须考虑交叉编译和体系结构差异。
- **正反示例**：✅ 使用make all-supported构建所有架构 / ❌ 只在本地架构编译
- **局限性**：某些架构可能由于工具链缺失而无法支持

### 🧠 3: 约束驱动设计 (Constraint-Driven)
DSM有严格的约束：包大小限制、权限沙箱、服务集成规范。优秀的SPK设计必须主动适应这些约束，而非被动应对。
- **正反示例**：✅ headless+server模式适配DSM / ❌ 硬要在DSM运行完整GUI应用
- **局限性**：某些功能可能因约束而必须删减或重设计

### 🧠 4: 并行开发可扩展 (Parallelizable)
架构应分解为可被多个开发者并行实现的模块。工作量大时无缝扩展开发人员。
- **正反示例**：✅ 分离"依赖编译"和"核心功能实现"两条线 / ❌ 单一大函数等待串行完成
- **局限性**：过度分解增加集成复杂度

### 🧠 5: 测试前置 (Test-First)
每个功能在发布前必须通过多个DSM版本、多个架构的兼容性测试。遗漏测试维度会导致用户反馈式bug。
- **正反示例**：✅ 构建所有架构+DSM 6.x&7.x的测试矩阵 / ❌ 只在开发机上测试
- **局限性**：测试环境维护成本高，需要自动化CI

### 🧠 6: 团队协调纪律 (Team Coordination)
项目经理必须确保任务清晰、依赖管理、风险透明。架构师的决策必须被开发者理解和遵守。
- **正反示例**：✅ 每日15分钟进度同步+风险提报 / ❌ 各自为政，集成时一片混乱
- **局限性**：协调有沟通成本，但省下的返工成本远高于此

### 🧠 7: 诚实的约束声明 (Honest Boundaries)
必须明确说出这个SPK做不到的功能、支持不了的DSM版本、无法优化的性能瓶颈。用户的失望来自期望落差。
- **正反示例**：✅ 「暂不支持DSM 6.x」 / ❌ 「完美兼容所有版本」
- **局限性**：诚实的声明可能让项目看起来有限制，但保护了用户信任

## 二、决策启发式 (10条快速判断)

1. **架构复杂度评分**：简单(CLI)=1, 中等(服务)=3, 复杂(GUI+依赖)=5。>3时必须启动架构师
2. **开发团队规模**：架构师识别的可并行模块数量。1-2个用单人，3+个需要扩展开发者
3. **DSM版本支持**：默认优先DSM 7.x，DSM 6.x需评估成本(+30-50%工作量)
4. **架构选择**：大型项目优先headless+server模式，避免GUI应用
5. **包大小目标**：<500MB为首选，500MB-2GB需要优化，>2GB需要架构调整
6. **测试覆盖**：至少3个关键架构(x64/ARM64/x86) × 2个DSM版本(7.x/6.x可选)
7. **CI/CD启动时机**：项目进入alpha阶段就应启动发布工程师和CI配置
8. **长期支持计划**：上市应用需要定期安全更新，需配置自动化发布流程
9. **风险升级路线**：遇到不可克服的技术障碍时，通过PM→架构师→决策者的链路上报
10. **扩展人员触发**：单开发者阻塞超过1周 OR 架构师识别的并行点>=3

## 三、团队协作工作流

### Phase 1: 项目启动 (PM驱动)
**参与者**: PM, 架构师, (可选)客户/需求方

**输出**: 项目启动文档、技术可行性报告、团队规模建议

| 步骤 | 责任人 | 任务 | 关键产出 |
|------|--------|------|---------|
| 需求分析 | PM | 收集项目目标、源项目特性、约束条件 | 需求清单 |
| 技术评估 | 架构师 | 评估源项目大小、依赖、DSM兼容性 | 技术可行性报告(PASS/RISK/FAIL) |
| 复杂度评分 | 架构师 | 根据启发式#1判断(1-5分) | 复杂度分级 |
| 团队规模决策 | PM+架构师 | 根据启发式#2判断需要多少开发者 | 初始团队配置 |
| 环境准备 | DevOps(可选) | Docker/OrbStack虚拟化环境搭建 | 开发环境就绪 |

**成功标准**:
- [ ] 需求清单明确(不模糊)
- [ ] 架构师给出可行性判断(PASS/RISK/FAIL)
- [ ] 团队规模已确定，是否需要扩展开发者已评估
- [ ] 开发环境已就绪

---

### Phase 2: 架构设计 (架构师驱动)
**参与者**: 架构师, PM, 可选核心开发者

**输出**: SPK技术方案、架构设计文档、编码规范

| 步骤 | 责任人 | 任务 | 关键产出 |
|------|--------|------|---------|
| 项目拆解 | 架构师 | 将源项目分解为可移植到SPK的模块 | 模块清单 + 依赖图 |
| 脱离GUI | 架构师 | 评估headless模式可行性，如何改造成服务端应用 | headless改造方案 |
| 依赖规划 | 架构师 | 列出所有外部依赖，哪些可用spksrc现有，哪些需要自建 | 依赖清单 + 获取策略 |
| 架构决策 | 架构师 | 定档：多进程vs单进程、内存预算、文件大小限制 | 架构决策表 |
| 并行工作分解 | 架构师 | 分解为可并行的开发任务，标记关键路径 | 任务分解图(带依赖) |

**成功标准**:
- [ ] 模块清单完整，开发者理解无歧义
- [ ] headless方案明确(可行/需要改造/不可行)
- [ ] 依赖清单完整，获取策略清晰
- [ ] 架构决策有量化约束(如最大包大小、目标内存)
- [ ] 并行任务分解，关键路径明确

---

### Phase 3: 并行开发 (开发者驱动，PM协调)
**参与者**: 开发者(×N), 测试工程师, PM, 架构师(问题解决)

**输出**: 构建脚本、功能代码、单元测试

| 步骤 | 责任人 | 任务 | 关键产出 |
|------|--------|------|---------|
| 依赖编译 | 开发者L2/DevOps | 为spksrc构建缺失的依赖包 | DEPENDS链路完整 |
| 核心实现 | 开发者(×N)并行 | 按架构设计编码功能模块 | 代码+单元测试 |
| 集成构建 | 开发者 | 合并代码，整体构建SPK | 可构建的源码树 |
| 自测 | 开发者 | 本地测试主要功能 | 自测报告 |
| 风险上报 | 开发者→PM→架构师 | 遇到阻塞或架构偏差时上报 | 风险日志+决策 |

**并行约束**:
- 开发者之间通过Git分支隔离，每日merge一次整合点
- 架构师预留每日1小时用于问题解决
- PM每日同步一次进度，识别阻塞

**成功标准**:
- [ ] 代码能完整构建（没有编译错误）
- [ ] 单元测试覆盖>=80%
- [ ] 依赖包都成功编译并链接
- [ ] 无重大架构偏差（小的优化可接受）

---

### Phase 4: 多维测试 (QA驱动)
**参与者**: 测试工程师, 开发者, 架构师

**输出**: 测试报告、缺陷清单、性能基线

| 步骤 | 责任人 | 任务 | 关键产出 |
|------|--------|------|---------|
| 测试矩阵建立 | QA | 根据启发式#6确定测试维度(架构×DSM版本) | 测试矩阵 |
| 环境部署 | QA | 在Docker/OrbStack中部署多个测试DSM环境 | 可用的测试环境 |
| 功能测试 | QA | 执行功能测试用例，测试主要流程 | 功能测试报告 |
| 兼容性测试 | QA | 验证x64/ARM/DSM6/DSM7等跨境场景 | 兼容性矩阵 |
| 性能基线 | QA | 测试启动时间、内存占用、CPU使用等 | 性能基线报告 |
| 缺陷上报 | QA→开发者→PM | 高优先级缺陷立即上报，中低优先级汇总 | 缺陷清单(优先级) |

**测试覆盖矩阵** (最小要求):
```
       | DSM 7.2  | DSM 7.1 | DSM 6.2 |
-------|----------|---------|---------|
x64    | ✅ 必测  | ✅ 推荐 | ❌ 可选 |
ARM64  | ✅ 必测  | ✅ 推荐 | ❌ 可选 |
x86    | ✅ 必测  | ❌ 可选 | ❌ 可选 |
```

**成功标准**:
- [ ] 所有P0缺陷已修复
- [ ] 至少完成"必测"矩阵中的所有场景
- [ ] 性能基线已建立
- [ ] 无重大兼容性问题

---

### Phase 5: 发布上线 (发布工程师驱动，PM协调)
**参与者**: 发布工程师, QA, 开发者, PM

**输出**: SPK安装包、发布文档、应用市场上架

| 步骤 | 责任人 | 任务 | 关键产出 |
|------|--------|------|---------|
| 最终构建 | 发布工程师 | 执行CI/CD流水线构建所有架构的最终版本 | 多架构SPK包 |
| 包验证 | 发布工程师+QA | 验证包的完整性、签名、元数据 | 验证报告 |
| 发布文档 | PM/开发者 | 编写安装指南、功能说明、已知问题 | README + 发布说明 |
| 应用市场提交 | 发布工程师 | 上传到DSM应用市场或私有仓库 | 应用市场链接 |
| 发布公告 | PM | 社区公告、更新日志 | 发布版本标签 |

**成功标准**:
- [ ] 所有架构的SPK包都已生成
- [ ] 包签名和元数据验证通过
- [ ] 发布文档完整（安装、使用、故障排查）
- [ ] 应用已上架或部署

## 五、团队扩展决策矩阵

### 何时扩展开发者 (L1/L2)
```
当以下条件任意满足时，启动第二个开发者：

✅ 架构师识别的可并行模块数 >= 3
✅ 单一开发者估计工作量 > 400小时
✅ 项目周期受限(如3个月内必须上线)且任务>200小时
✅ 出现串行阻塞(一个任务被另一个任务完全卡住)超过1周
```

### 何时加入发布工程师
```
当项目进入以下阶段时，启动发布工程师：

✅ Alpha阶段（需要自动化CI/CD）
✅ 计划定期发布(月度以上)
✅ 需要多架构并行构建
✅ 需要自动化测试和验证流程
```

### 何时加入DevOps管理员
```
当出现以下情况时，启动DevOps：

✅ 多个项目同时进行，环境配置重复
✅ CI/CD流水线配置复杂(>5个stage)
✅ 需要定期更新工具链(gcc, spksrc, DSM SDK)
✅ 测试环境需要自动化部署和清理
```

## 六、通用工具和环境

### 开发环境规范
- **虚拟化方案**：macOS用OrbStack + Docker; Linux直接Docker; Windows不支持(使用WSL2 Linux VM)
- **基础镜像**：`ghcr.io/synocommunity/spksrc:latest`
- **工作目录**：`~/synology-spk-workspace/`
- **构建输出**：`packages/` 目录(多架构SPK)

### 关键脚本（位于`scripts/`目录）
- `init-workspace.sh` — 初始化开发环境，拉取spksrc框架
- `setup-orbstack-vm.sh` — OrbStack虚拟机一键配置(仅macOS)
- `build-all-archs.sh` — 批量构建所有架构(x64/ARM/etc)
- `validate-spk-package.sh` — SPK包完整性和元数据验证
- `run-test-matrix.sh` — 运行完整的多版本多架构测试

## 七、诚实边界

### 我们能做的 ✅
1. 将开源项目(包括大型项目如vscode)的源码改造为SPK套件
2. 设计和实施多架构(x64/ARM/ARM64/x86)交叉编译
3. 适配DSM 7.x(主要)和DSM 6.x(遗留)
4. 从CLI工具到服务应用的全栈开发支持
5. 多DSM版本/多架构的兼容性测试
6. 自动化CI/CD流水线构建和发布
7. 大型项目的需求分解和并行开发协调

### 我们做不到的 ❌
1. **完整的Electron/GUI应用**：DSM沙箱限制，vscode必须headless服务端模式
2. **超大包(>2GB)**：会超过DSM安装限制，需要架构调整(分割、去冗余等)
3. **实时渲染应用(如3D游戏)**：DSM无GPU支持，性能不可接受
4. **Windows/macOS应用的原生移植**：只能通过虚拟机，不支持直接编译
5. **无源码的闭源项目**：必须有源码才能编译

### 信息时效性和局限
- 基于2026年5月的spksrc和官方DSM SDK文档
- SPK工具链持续更新，某些细节可能过时
- 新的DSM版本(8.0+)的规范暂未支持
- 群晖的签名证书和应用市场规范需要定期更新

## 八、快速开始

1. **创建初始项目**：
   ```
   pm> 我想把vscode移植为SPK，需要多少人？需要多久？
   architect> [评估可行性，给出时间和人员建议]
   ```

2. **启动团队**：
   ```
   pm> 启动架构设计，目标DSM 7.2, x64/ARM64, 预算时间3个月
   architect> [开始方案设计，列出拆解模块和依赖]
   ```

3. **并行开发**：
   ```
   developer> 我拿到架构文档，开始编码依赖编译和核心模块
   pm> [每日协调进度，识别阻塞]
   ```

4. **测试和发布**：
   ```
   qa> 环境就绪，开始多维测试
   release-engineer> [自动化构建所有架构，准备发布]
   ```
